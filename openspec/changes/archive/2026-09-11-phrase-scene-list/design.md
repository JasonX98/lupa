## Context

见 `proposal.md` 的 Why。设计只受以下既有事实约束：

- `phrases.scene` 是 `TEXT NOT NULL DEFAULT ''` 的单值列（`desktop/lib/data/schema.sql`），`scene_tag` 是短语级的语域标签。`scene` 的全部消费点只有 5 处：表单（`phrase_page.dart:806` 单行窄框）、详情弹窗（`:537`）、复习页（`phrase_review_page.dart:340`）、CSV（`phrase_csv.dart:58`）、apkg（`phrase_apkg.dart:117`）。
- 表单既有约定：叙述型字段给行数（释义 `maxLines: 2`、典故 `maxLines: 3`），结构化字段走可增删行（例句 `phrase_bits.dart:136`）。「使用场景」两者都不占。
- 项目约束：`schema.sql` 是唯一事实源，仅用 SQLite ≥ 3.38 标准 SQL；旧库迁移靠 `PHRASE_TABLES_V2` marker 区块 + 抬 `schema_version`（`notebook_db.dart:49`）。因此**任何新表都要付一次迁移与回填的账**。
- apkg 字段内容当前是裸字符串拼接（`phrase_apkg.dart:117` 的 `_block()`），既无 HTML 转义，也不把换行转成 `<br>`——典故（表单已允许 3 行）今天导出的换行就会被 HTML 折叠。

## Goals / Non-Goals

**Goals:**

- 让「使用场景」既能容纳多条独立场景，也能把单条场景内容看全。
- 保持 `phrases.scene` 单一 `TEXT` 列、`schema_version` 停在 2：零迁移、零回滚成本、老数据无损。
- 让「多条场景」在 apkg 里呈现为真正的列表，并顺手修掉既有导出缺陷（转义缺失、多行被折叠）。

**Non-Goals:**

- 不引入 `phrase_scenes` 子表，不做每场景独立标签/排序/查询。
- 不做可拖拽调高的输入框。
- 不改动调度、统计、标签筛选、CSV 列集合与单词侧任何输出。

## Decisions

### D1. 用「可增删场景行」承载多条，仍存单列 `TEXT`，以 `\n` 分隔

- **选择**：表单渲染 N 个场景行（照 `ExampleEditRow` 的范式），保存 `join('\n')` 进 `PhraseInput.scene`，读入 `split('\n')`。
- **理由**：`schema.sql` / `phrase_csv.dart` 零改动，`repo.dart` 只在写入处包一层归一化（见 D2）；老库单行场景天然等于「一条场景」，无需回填；`\n` 是纯文本可读可编辑，CSV 里就是一格多行。
- **替代方案 A（一个大 textarea，一行一条靠自觉）**：代码最少、视野最大，但无法强制「一条一行」。用户在长句里折行就会多出一条场景，直接污染 apkg 的 `<li>`——而 `<ul><li>` 精确分条正是本需求的一部分，故放弃。
- **替代方案 C（子表 `phrase_scenes`）**：语义最干净，每条场景可任意多行、可排序、可独立加标签。但要付 `schema_version` 抬到 3 + 旧数据回填 + `repo` 全链改 + 3 个测试文件重写。用户已确认不需要每场景独立标签，3 条短句不值这张账，故放弃。

### D2. 不变式：「一条场景 = 一行」，`\n` 只在条与条之间出现

- **选择**：场景行内不允许存在 `\n`。`Enter` 视为「新增下一条场景」而非折行；粘贴/输入带来的换行同样按行拆成多条；空条目保存时丢弃。场景行用 `maxLines: null` 只做**视觉**换行（word wrap 不产生 `\n`），因此「看全内容」与「`\n` 分隔无歧义」可以同时成立。
- **理由**：这是 D1 能成立的前提。若允许条内换行，`'\n'` 就同时是分隔符和内容，导出必然分错。把规则收敛成一句可解释的话（"回车 = 新增一条场景"），比引入子表便宜得多。
- **落点（双层）**：`splitScenes`/`joinScenes` 是唯一入口。UI 表单负责把行拆 / 合；`repo.dart` 的 insert 与 update 再包一层 `_normalizeScene`——因为 spec 的「空白场景条目 MUST 在保存时被丢弃」是**系统**级保证，不能只靠 UI 调用方自觉（`tool/verify_*.dart` 与将来的导入路径都直接调 repo）。两层都是幂等的。
- **替代方案（保存时把条内换行折叠为空格）**：数据同样精确，但中文里会平白多出空格，且用户折行排版静默消失。只作为 IME 风险（D3）的退路保留。

### D3. `Enter` 拦截，IME 风险配一条退路

- **选择**：在场景行上拦截回车键事件转为「新增下一条场景」，且拦截时先判 `TextEditingController.value.composing.isValid`——组字中（中文输入法候选未上屏）则放行给输入法确认候选，否则才新增场景行。
- **理由**：用 composing 状态判断而不是依赖平台是否把回车送成 key event，两种情形就能确定性共存，不必赌 IME 行为。
- **退路**：若实机仍出现组字回车误触发新增，则退回 D2 的替代方案：`Enter` 照常换行，保存时把条内换行归一为空格（数据不变式与全部 spec scenario 同样满足）。

### D4. apkg：场景渲染为 `<ul><li>`，并补 HTML 转义与多行保留

- **选择**：`_block()` 增加 HTML 转义（`<`、`>`、`&` 等），并把多行值按情况渲染——场景走 `<ul class="scene-list"><li>…</li></ul>`，典故等纯文本多行按 `<br>` 连接；新增 `.scene-list` 样式。
- **理由**：转义是正确性问题，不是美化：用户在本应用里记的是**英文**短语与例句，`<`、`&` 完全可能出现（数学符号、`<something>` 占位写法）。多行折叠同理——典故今天就在踩这个坑。两处都在同一个 `_block()` 路径上，合并修改比拆两次改同一函数更安全。
- **替代方案（只转义场景、不动典故）**：留下同一函数里两种行为，后续必然被误用，故一并统一。

### D5. 表单栅格重排

- **选择**：`场景标签`（160px）与 `标签` 并排成一行，`使用场景` 独占下一行全宽（560px），其下是 N 个场景行 + 「+ 加一条场景」。
- **理由**：当前把场景挤在标签右侧约 370px 是「看不全」的另一半原因；与「例句」区块上下相邻也更成体系。

## Risks / Trade-offs

- [中文 IME 组字时的 `Enter` 被误判] → D3 的 composing 判断 + 退路（保存时归一为空格）；两种行为都不改 spec，故可在实现期定。
- [用户想在一条场景里写多段文字] → 与 D2 不变式冲突，编辑体验上会「咬」他一口（回车变新增）。这是选 B1 换取零迁移的代价；真需要时升级到方案 C，且旧数据 `split('\n')` 可无损灌进子表。
- [旧数据出现空行/前后空白] → 读入时丢弃空条目、统一 `trim`，避免 `split` 产生幽灵场景；写入侧在 repo 层兼底（D2 落点）。
- [HTML 转义改变已导出卡片的字段内容] → guid 稳定，重新导入会在 Anki 端**更新**同一张卡而非新建；这本身是修 bug，但用户会看到卡片外观变化，需在 tasks 里作为可见影响写进验证步骤。
- [CSV 场景列变成多行单元格] → `csv` 包已对含换行的字段自动加引号（现有多行「例句」列已依赖此行为），Excel 可正确解析；无需改导出代码，但要补断言。
- [详情/复习两处渲染分叉] → 两条路径都要按条渲染，若只改一处会出现「详情 3 条、复习 1 段」的不一致，故列为同一任务的相邻改动。

## Migration Plan

- **数据迁移：无。** `schema_version` 保持 2，`phrases.scene` 类型不变；老库老数据（单行）读出来就是「一条场景」，新写的多条也只是同一列里多了换行。
- **回滚**：仅还原代码即可。回滚前写入的多条场景在旧版本里显示为一整段文本（`\n` 在 `Text` 中仍换行显示），数据不损坏，可双向兼容。
- **验证顺序**：`dart run tool/verify_phrase_repo.dart`（多条 round-trip + apkg/CSV 断言）→ `flutter test`（详情弹窗多条渲染）→ `flutter analyze`。

## Open Questions

- 中文输入法组字时 `Enter` 的 composing 判断在 Windows 实机上是否足够——需实测确认。答案只决定采用 D3 首选或退路，两者都在现有 spec 内，不改变 spec、方案或任务拆分。
