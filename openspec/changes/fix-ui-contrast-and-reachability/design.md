## Context

见 `proposal.md` 的 Why。设计只受以下**实测**事实约束（本轮全部用 WCAG 2.x 公式算过，并用主题注释自称的 17.2 / 7.8 / 4.8:1 自检通过）：

- 主题的文字色是健康的，全部达标：

```
tx1 on surface   17.19:1  ✓    tx1Dark on surfaceDark   12.85:1  ✓
tx2 on surface    7.75:1  ✓    tx2Dark on surfaceDark    7.75:1  ✓
tx3 on surface    4.84:1  ✓    tx3Dark on surfaceDark    5.67:1  ✓
jade 强调 on surface 5.10:1 ✓   jadeDark on surfaceDark  6.92:1  ✓
```

- **唯一的缺陷类别是把 `outline` 当前景色**：主题把 `outline` 映射到 `border`（`#E4E2DD`），实测 `outline on surface = 1.29:1`、`outline on bg = 1.20:1`、深色 `outline on surfaceDark = 1.23:1`。
- 主题**没有显式映射 `onSurfaceVariant`**（用的是 `ColorScheme.fromSeed` 的生成值）。实测该值恰好是合格的：浅色 `#3F4946` ≈ 9.3:1、深色 `#BEC9C5` ≈ 8.2:1。也就是说——**「弱化前景色」这个 token 一直存在且合格，只是没人知道它可用**：主题里没有注释、没有语义命名，而 `tx3` 只通过 `bodySmall` 间接暴露。开发者需要「灰色」时手边看起来最像的就是 `outline`。
- 剩余 7 处误用（上一轮 `add-ai-word-enrichment` 已修掉它自己引入的 2 处）：

```
app_shell.dart:192     侧栏导航图标（未选中态）      ← 主要交互入口
app_shell.dart:204     侧栏快捷键提示文字（10.5px）  ← 唯一的「文字」误用
app_shell.dart:261     侧栏「设置」图标               ← 主要交互入口
search_page.dart:423   查词空状态大图标 44px          ← 装饰性
search_page.dart:835   收藏星标（未收藏态）            ← 主要交互入口
notebook_page.dart:135 生词本空状态图标 48px          ← 装饰性
phrase_page.dart:273   短语集空状态图标 48px          ← 装饰性
```

- 侧栏结构是 `SizedBox(width: 208) > Column`（`app_shell.dart:212`），**无滚动**。实测最小高度约 373px（340px 溢出 33px、300px 溢出 73px，线性）。`windows/runner/main.cpp` 只设初始尺寸 1280×720，**未设最小窗口尺寸**，因此这是用户可达的状态。
- 项目既有先例：`desktop/lib/widgets/centered_scroll_view.dart` 就是为「复习页在矮窗口下不裁剪内容」写的（空间够则居中、不够则滚动）。侧栏要的是它的**变体**：空间够则保持原布局（不是居中），不够则滚动。
- 项目既有测试先例：`test/ai_text_contrast_test.dart` 已把「对比度」变成可机械验证的断言（按 WCAG 公式算而非断言色值），并已包含图标分支。
- **实施期补充实测（全量审计 `test/ui_contrast_test.dart` 的产出）**：修完 7 处后，五个受检区域里的图标**全部达标**（本次修复的 7 处均为 8.63:1；收藏星标 9.32:1）；**深色主题零违例**。浅色主题另剩 15 处文字违例，但它们归为 **4 个 (前景, 背景) 组合**，与 `outline` 根因无关：

```
E1  tx3Light #6E736D on bgLight        #F7F6F3  4.48:1  ← 提案「顺延」已接受
E2  tx3Light #6E736D on surfContHighest #EFEEE9  4.17:1  ← 新发现（「词频」徽章）
E3  jade     #0E7C6B on jadeSoftLight  #E7F2EF  4.46:1  ← 新发现（选中态导航项）
E4  tx3Light #6E736D on jadeSoftLight  #E7F2EF  4.23:1  ← 新发现（高亮统计 chip）
```

  即：**spec 里「所有文字 ≥4.5:1」在浅色主题下今天并不字面成立**。E2/E3/E4 已登记进 proposal 的「顺延」节；为什么不能在本次顺手修、以及断言边界怎么画，见 D5。

## Goals / Non-Goals

**Goals:**

- 让「弱化前景色」在主题里成为一个**有名字、有注释、有实测数值**的 token，使误用不再是最省事的选择。
- 把 7 处误用一次性收敛，且用**能算对比度的测试**守住这一类，而不是靠肉眼复查。
- 让侧栏在任意窗口高度下可用，同时**保证空间充足时布局零变化**（不引入视觉回退）。

**Non-Goals:**

- 不重做配色、不改正文色（它们已达标）。
- 不改布局比例、间距、字号。
- 不为「短语集筛选圆点」这类装饰性图形设阈值（spec 只管文字与 UI 组件）。
- 不设 Windows 最小窗口尺寸（选择了「让界面适应任意尺寸」而非「限制尺寸」）。

## Decisions

### D1. 根因修复：显式映射 `onSurfaceVariant` 并写清语义边界

- **选择**：在 `_buildLupaTheme` 的 `copyWith` 里**显式**设置 `onSurfaceVariant`（取当前实测达标的那个值），并在该行上方加注释：*它才是弱化前景色；`outline` 是边框色（1.2:1），只能描边*。
- **理由**：这是个「缺席导致的误用」——不是有人故意选错了颜色，而是没有一个明显正确的选择。显式映射 + 注释把默认选择变成正确选择。同时显式映射还消除了一个真实风险：当前值是 `fromSeed` 的生成结果，Flutter 调整算法就可能漂移，而它现在承载了 7 个站点的可读性。
- **替代方案 A（只改 7 处调用点，不动主题）**：改动更小，但根因留着——下一个需要「灰色」的人还会拿 `outline`，而这次修复的教训只活在代码注释里。
- **替代方案 B（把 `outline` 直接改成深灰）**：会同时毁掉所有描边（边框、分隔线、输入框轮廓），因为它们都指望这个浅色。放弃。
- **替代方案 C（新增自定义扩展 `ThemeExtension`）**：语义最干净，但项目已有 `tx2`/`tx3` 这套命名且 `ColorScheme` 是唯一被各处读取的入口，新增一套抽象层换不来对等收益。

### D2. 7 处统一改为 `scheme.onSurfaceVariant`

- **选择**：全部改成 `scheme.onSurfaceVariant`，其中 3 处「未选中态」的三元表达式只替换 else 分支（选中态继续用 `primary`）。
- **理由**：一处根因、一个替代值，统一才可解释。实测 9.3:1 同时满足「文字 ≥4.5」与「图标 ≥3」两个门槛，不需要为两类分别选色——**分两套色反而会让人再犯「这次该用哪个」的错**。
- **替代方案（装饰性图标用更淡的色）**：空状态大图标本来是装饰性的，理论上可以更淡。但「淡到多少」没有客观依据，而且它同时是那个空状态唯一的视觉锚点；统一用同一个 token 更好维护。

### D3. 侧栏加滚动，但**空间充足时布局零变化**

- **选择**：把侧栏的 `SizedBox > Column` 包进 `LayoutBuilder` + `SingleChildScrollView`，仅在内容超出可用高度时才滚动；不超出时 `Column` 撑满、`Spacer()` 继续把「设置」入口顶到底部。
- **理由**：既有 `CenteredScrollView` 的做法是「够则居中、不够则滚」，而侧栏要的是**「够则撑满（保持贴底）、不够则滚」**——不能直接复用它（居中会让品牌区跑到中间）。用 `LayoutBuilder` 判断 `maxHeight` 与内容高度，或更简单：`SingleChildScrollView` 内放一个 `ConstrainedBox(minHeight: 可用高度)`，让 `Spacer` 在空间充足时仍能把设置顶到底。后者不需要预先知道内容高度，更稳。

  实现要点（`Spacer` 在无界高度下会失效，必须先约束住）：
  ```
  LayoutBuilder
    └ SingleChildScrollView
        └ ConstrainedBox(minHeight: 可用高度)
            └ IntrinsicHeight? 或 Column(children: [...nav, Spacer(), 设置])
  ```
  `Spacer`（`Expanded`）在 `SingleChildScrollView` 的无界高度下会抛错，所以必须靠 `ConstrainedBox(minHeight:)` + `IntrinsicHeight` 组合，或改成「不足时补一个 `SizedBox` 撑开」的显式做法。**具体手法在实现时确定，但「空间充足时与现在逐像素一致」是硬要求，且要用测试守住。**
- **替代方案 A（设置 Windows 最小窗口尺寸）**：一行代码解决，但改变了「用户能把窗口拖多小」这个产品行为；而且它只解决侧栏，其他页面未来同样可能有此问题。放弃。
- **替代方案 B（矮窗口时隐藏快捷键提示文字）**：省一点高度，但治标；且侧栏本身的固定项（品牌区 + 5 个导航 + 设置）在 300px 高度下无论怎么省都放不下。

### D4. 用「算对比度」的测试守这一类，而不是断言色值

- **选择**：新增测试按 WCAG 公式计算每个文字/图标前景色相对其背景的对比度并断言下限；坐标这类"布局语义"用 `getRect` 断言（如「设置」入口在矮窗口下仍可点、空间充足时其底部与侧栏底部对齐）。
- **理由**：上一轮已经验证过两种测试的差别 —— 断言色值的测试改个色号就碎且不解释为什么；算对比度的测试直接编码了「可读」这个意图，并且能算出具体数字（实测正是它报出了 `1.29:1` 这个可行动的结论）。布局同理：断言「可点」「贴底」比断言像素值稳。
- **测试必须能证明自己会失败**：7 处误用中要挑代表性站点做反向验证（改回 `outline` 后测试转红），否则无法区分「测试有效」与「测试什么都没测」。

### D5. 对比度断言的**边界**：受检站点全达标 + 既有例外显式登记（而非「全应用全达标」）

- **背景**：任务 4.1 字面要求断言「**所有**文字 ≥4.5:1」。实测发现浅色主题有 4 类既有例外（见 Context 里的 E1~E4），其中 E1 是提案自己已接受的、E2~E4 是本次新发现。
- **选择**：测试断言两个东西 ——（a）**本次修复涉及的站点全部达标**；（b）4 类既有例外在 `_exceptionsFor` 里**逐条登记**（带实测值与来源），并由一个「允许清单不得腐烂」的用例要求每条登记**仍被命中**。未登记的违例一律转红。
- **理由**：「所有文字全达标」在今天**是假的**，把它写成断言只会得到两种结果 —— 要么测试永久红，要么把阈值降到能过（等于静默放宽 spec）。而登记制把「已接受的例外」从口头共识变成可执行断言：新增违例 → 红；例外被修好 → 红（催删条目）；例外色值漂移 → 红（催重评）。因此它既不会静默扩大，也不会腐烂。
- **替代方案 A（扩大本次范围把 E2~E4 修掉）**：要动 `tx3Light` 或各站点底色/选中态前景 —— 触碰非目标「不重做配色方案」，且 E3/E4 要改的正是任务 2.1 明确要求「选中态保持 `primary`」那一支。属于独立决策。
- **替代方案 B（只断言颜色「不等于 outline」）**：能守住根因，但守不住「换成另一个不达标的颜色」，且不改色号就永远绿；比「算对比度」弱。
- **替代方案 C（阈值降到 4.1 / 只查图标）**：等于把 spec 收窄且不落文字记录。放弃。
- **反面验证（必须能红）**：D4 已要求，实施时两向都验过 ——（1）把侧栏图标 / 快捷键提示 / 收藏星标改回 `outline` → 4 个用例转红并打印 **浅 1.20:1 / 1.29:1、深 1.37:1 / 1.23:1**；（2）往登记里塞一条未命中的假例外 → 「不得腐烂」用例转红（`Expected [E1..E4, E9] / Actual [E1..E4]`）。
- **已知局限**：该「不得腐烂」用例依赖同文件内用例的执行顺序，所以**不能用 `--plain-name` 单跑它**（会因 `_hits` 为空而假红）；跑整个文件才有效。

## Risks / Trade-offs

- [侧栏加滚动后「设置」入口不再贴底] → 这是本次最主要的视觉回退风险。D3 明确要求空间充足时逐像素一致，并用测试断言「足够高时设置入口与侧栏底部对齐」。
- [`Spacer` 在无界高度下报错] → `SingleChildScrollView` 给子项无界高度，`Expanded`/`Spacer` 会抛 `RenderFlex` 异常。这是实现期最容易踩的坑，D3 已记录两种可行手法。
- [`onSurfaceVariant` 的显式取值可能与 `fromSeed` 生成值略有差异，导致视觉上微调] → 取值时以「当前实测达标的那个颜色」为准，使改动在视觉上尽量不可见；该 token 目前只影响本次要修的 7 处（改动前它们用的是 1.29:1 的浅色，所以视觉上必然是变深——这是修复本身的目的）。
- [装饰性空状态图标由浅变深后，空状态显得更"重"] → 三处空状态图标从 1.29:1 变到 9.3:1 是明显变化。若实机观感过重，退路是给装饰性图标单独取一个介于两者之间、但仍 ≥3:1 的值 —— **这不违反 spec**（spec 只要求 ≥3:1），但需在实现期看一眼实机再定，不要预先优化。
- [对比度测试的背景色是硬编码的（surface/bg）] → 若将来某段文字被放到新底色上，测试不会自动发现。缓解：测试以「主题色值」为准而非魔数，且只覆盖本次涉及的页面；后续新增底色时按同一模式补案例。

## Migration Plan

- **数据迁移：无。** 不涉及 schema、不涉及 `config.json`、不涉及任何存量数据。
- **回滚**：仅还原代码。无状态残留。
- **验证顺序**：`flutter analyze` → `flutter test`（含新增的对比度与侧栏测试，以及反向验证：改回 `outline` 应转红）→ 八组 `verify_*.dart`（应全部保持 0 失败，证明纯界面改动没有触碰数据层）→ 手动看一眼浅/深主题下的侧栏与空状态观感。
- 不涉及版本号变更（纯修复，随下次发版；若要单独发补丁版，按 `pubspec.yaml` 唯一事实源改两处）。

## Open Questions

- **装饰性空状态图标的最终色**：统一用 `onSurfaceVariant` 是 D2 的默认；若实机看下来空状态过重，可在 ≥3:1 的前提下单独取一个中间值。这属于观察后调优，不影响 spec（只要求 ≥3:1）、不影响方案结构、不影响任务拆分。
